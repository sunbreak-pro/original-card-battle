docs のコンフリクトは、正本の一覧表の書き方を変えれば大半が消えます

9 月 24 日以降に起きたコンフリクト 9 件のうち 7 件は、正本の一覧表（.claude/docs/SOURCES.md）の 1 枚で起きていました。原因は、表の桁揃えが毎回やり直されることと、版を上げるたびに一覧表も書き換える決まりの 2 つです。

  • 今日から

    1. 表の桁揃えを止めます

    編集のたびに走る整形ツールが、表の 1 マスが長くなると表全体の空白を詰め直しています。整形の設定を 1 行足すと、幅の広い表は桁を揃えない書き方になります。

  • 今日から

    2. 一覧表を持ち主ごとに分け、版を書かないようにします

    状態の欄から版の番号と経緯を外し、版を上げても一覧表に触らないようにします。表は持ち主の担当ごとに分け、別々の担当の行が隣り合わないようにします。

  • 今日から

    3. 同じ担当の続きの PR は前の PR の上に積みます

    同じ担当が同じ設計書を触る PR を 2 本出すときは、2 本目のブランチをマージ待ちの 1 本目から切ります。設計書の版の行と改訂履歴の取り合いが起きなくなります。

  • 必要になったら

    改訂履歴を別ファイルにして自動で両方残す

    3 を守っても改訂履歴でぶつかり続けたら、履歴を設計書の外に出し、git の union（両方の行を残す合流のしかた）を設定します。

  • 入れない

    マージキューや一覧表の自動生成

    今の衝突は書き方で起きているので、仕組みを足す前に書き方で消せます。docs の書き込みを main のチャットだけに集めるのも、待ち行列が増えるので入れません。

たとえると、町内会の回覧板に全員が 1 行ずつ書き込む形です。そこへ、誰かが書くたびに回覧板をまるごと清書し直す人がいます。清書の分だけ全員の書き込みとぶつかります。対策 1 は清書をやめることで、対策 2 は回覧板を班ごとの用紙に分けることにあたります。

表全体が書き換わる仕組み

グローバル設定の hook（~/.claude/hooks/post-edit-prettier.mjs）が、Edit と Write のたびに .md へ prettier（コード整形ツール）をかけています。prettier は Markdown の表の列幅を、いちばん長いマスに合わせて揃えます。デザインの担当が「戦闘画面とカードの見た目」の行の状態の欄に経緯を書き足すたびに列が広がり、表の 31 行すべてに空白が足されていました（#254 で 61 行、#259 で 31 行）。この書き換えがマージされると、その時点で一覧表を触っている他の担当の PR がすべてぶつかります。

対策 1：表の桁揃えを止める

リポジトリの直下に prettier の設定を置き、Markdown だけ proseWrap: "never" にします。この設定のとき prettier は、揃えると 80 桁を超える表を | a | b | の詰めた形で書きます。設定はファイルの場所からさかのぼって読まれるので、各担当の作業場所（worktree）でも同じに効きます。

// .prettierrc.json
{ "overrides": [{ "files": "*.md", "options": { "proseWrap": "never" } }] }

いまの docs に試しにかけると、変わる行のほとんどは表の空白でした。battle_core_v4.md では変わる 404 行のうち 397 行が表の行で、残りは段落の折り返しの結合です。

入れ方に注意が要ります。設定だけを入れると、各担当が次にファイルを触ったときにそのファイル全体が詰め直され、移行の間だけ衝突が増えます。docs の PR が 1 本も開いていない時点で、設定と全 Markdown の詰め直しを 1 本の PR にしてマージします。

対策 2：一覧表を持ち主ごとに分け、版を書かない

  • 状態の欄は種類だけにします。APPROVED / DRAFT / PROPOSED / 現行と「§N 未反映」の印だけを書きます。版の番号と「いつ何を入れ込んだか」は、設計書自身の冒頭と改訂履歴に任せます。
  • 版を上げても一覧表に触らない決まりにします。いまの決まり（「版を上げるコミットで本書の行を含める」）を外し、一覧表を書くのは正本を足す・使わなくする・持ち主を変えるときだけにします。これで普段の PR は一覧表に触らなくなります。
  • §2 の表を持ち主ごとに分けます。main・battle・cards・design・dungeon の小見出しの下にそれぞれ表を置き、表の下の但し書きもその担当の節へ移します。担当の違う変更のあいだに小見出しの行が挟まるので、git は両方を自動で合流できます。
  • 読み取りのスクリプトを直します。scripts/sources.mjs の tableRows は §2 の中の表を 1 つと見なしています。複数の表の見出し行と区切り行を飛ばすように直し、npm run sources -- --check に「状態の欄が長すぎる行」の検出を足します。

対策 3：同じ担当の続きの PR は積み重ねる

担当ごとの作業場所は 1 つのチャットで順に進みますが、PR はこうだいさんのマージ待ちのあいだに次のブランチを main から切っています。そのため同じ担当の 2 本の PR が、同じ設計書の版の行と改訂履歴の末尾を同時に書いていました。2 本目が同じ設計書を触るときは git switch -c <次> <マージ待ちのブランチ> で切り、PR 本文に「#前の PR の上に積んでいます」と書きます。1 本目がマージされると、2 本目の差分は自分の変更だけになります。この決まりは worktree の運用の手順書（worktree-policy スキル）に 1 項目足します。

置いた仮定

  • 一覧表の「状態」の欄に版を書いているのは、版を一覧で見るためだと考えました。版は設計書の冒頭で見られるので、一覧表から外しても困らないと判断しています。
  • 担当の違う PR どうしが同じ設計書の本文を同時に書き換えることは、one writer per artifact（1 つの文書を書くのは 1 つの担当だけ）の決まりで起きない前提にしています。実測でもこの形の衝突はありませんでした。

未確認のこと

  • GitHub の PR 画面のマージボタンが、git の union の設定を守るかは確かめていません。「必要になったら」の案を入れるときに確かめます。各担当の作業場所で git merge origin/main するときは守られます。
  • 80 桁に収まる小さな表は、設定を変えたあとも桁が揃います。日本語は 1 文字を 2 桁と数えるので、docs の表の多くは 80 桁を超えますが、全部の表では確かめていません。

次に判断が要る点

  • 3 つの対策を 1 本の PR にまとめて入れてよいかを決めてください。対策 1 の詰め直しは docs の PR が開いていない時点で入れる必要があり、今は docs を触る PR が 3 本開いています（#331・#332・#337）。#331 と #332 はどちらもカードの担当で、一覧表と敵ロースターの両方を触っているので、片方をマージするともう片方がぶつかる見込みです。
  • prettier の hook はグローバル設定にあるので、ほかのプロジェクトの Markdown の表も同じように詰め直されています。ほかのプロジェクトにも同じ設定を入れるかを決めてください。
