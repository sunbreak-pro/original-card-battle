判断2026-10-19

既製ツールの unity-cli-loop で、札のドラッグまで Claude が実機で動かせました

Claude が Unity のゲーム画面を、Playwright MCP のように動かせるかを試しました。試験は 2026-10-19 に、Unity 6000.5.5f1 の Editor で行いました。札を掴む、動かす、離す、「ターン終了」を押す、札のホバーを出す、の操作が実機で通りました。足りないのは、1 フレームごとの数字です。

  • 16件の出典
  • 約 11 分で読めます（推定）
  • できた

    札の操作が、実機で最後まで通りました

    unity-cli-loop（星 582、MIT）を Unity のプロジェクトに入れ、Battle.unity を Play しました。札を出す、間合い外で拒否される、「ターン終了」を押す、札のホバーを出す、の流れを、Claude が動かせました。画面も撮れました [16]。

  • 足りない

    フレームごとの動きは、まだ数字になりません

    uloop の呼び出しは 1 回で 0.3〜1.5 秒かかり、その間に Editor は約 450〜550 fps で回ります（計算）。掴んでいる間の札の位置は、2〜3 点しか読めません [16]。

  • Issue にした

    記録する部品を、Issue #643 にしました

    ドラッグの間の札と受け皿の状態を、フレームごとに JSON で記録する部品を、battle（戦闘）担当の Issue にしました。Editor なしの Windows ビルドで動かす案は、記録の中身を見てから決めます。

最初の調査では、いまのゲームがドラッグを Pointer.current から読むと見ていました。そのため、画面の部品へクリックを送る道具は、ドラッグに届かないと書きました。この見立ては誤りでした。札のドラッグは CardView の EventSystem の処理で動き、Pointer.current を読むのは「ターン終了」の押下と札のホバーです。道具ごとに届く先が違い、unity-cli-loop の 2 つの道具を使い分けると、1 ターンの操作がすべて届きました。実機で確かめる前に書いた予測が外れたので、この報告書は試験の結果で書き直しています。

02訂正

最初の見立ては誤りで、札のドラッグは EventSystem で動いていました

  • 札のドラッグは、EventSystem の処理で動きます。CardView が IBeginDragHandler・IDragHandler・IEndDragHandler を実装しています（CardView.cs:18）。
  • ドラッグを受けるのは、DepictionPlayer の OnDragBegan・OnDragMoved・OnDragEnded です（DepictionPlayer.cs:2105〜2125）[14]。
  • Pointer.current を読むのは、「ターン終了」の押下（:693）、札のホバー（:1944）、用語のホバー（:1910）です [14]。
  • 「ターン終了」は Button を持たず、押した位置を RectTransform の範囲で判定します。EventSystem へ送る道具は、ここに当たりません。
入力の送り方で、届く操作が分かれます。
道具入力の送り方届いた操作届かなかった操作
simulate-mouse-ui [4]画面の部品へ、ポインタのイベントを送ります（EventSystem）。札のドラッグ、メニューのボタン。「ターン終了」。
simulate-mouse-input [4]Input System のマウスへ、押す・離す・位置を書きます。「ターン終了」、札のホバー。札のドラッグは試していません。押したまま動かす呼び出しが、文書にありません。
  • Funplay の simulate_mouse_click [12] と playcaller [15] も、EventSystem へ送る方式です。simulate-mouse-ui と同じ結果になる見込みです（推定）。
  • 操作ごとに Claude へ往復する方式（Windows-MCP [13]、Playwright MCP の標準のドラッグ [7]）は、100 ms 単位の動きを作れません。DragMove は --drag-speed で速さを指定でき、試験では 400〜800 px/s で動きました。

04残る穴と注意

止まる所は、フレーム単位の記録、フォーカス、Editor の占有の 3 つです

止まる所は 3 つあり、対処はどれも決まっています。
止まる所起きたこと対処
フレーム単位の記録uloop の呼び出しは 1 回で 0.3〜1.5 秒かかります。Time.frameCount は 0.525 秒で 124263 から 124499 へ進み、Editor は約 450 fps で回っていました（計算）。札の追従の曲線と、受け皿の判定が切り替わる瞬間は、数字になりません。Issue #643 の部品で記録します。
フォーカスInput System の既定は、Game ビューにフォーカスがないとポインタの入力を止めます [9]。試験では、Application.isFocused が False になる場面があり、uloop focus-window で True に戻りました。自分で QueueDeltaStateEvent に書いたマウスの位置は、読み返すと別の値で、ホバーが出ませんでした。原因は未確認です。道具の simulate-mouse-input を使います。操作の前に uloop focus-window を呼びます。
Editor の占有と安全試験の間は Claude が Editor を操作するので、同じ Editor を人が使えません。execute-dynamic-code は、Editor の中で任意の C# を動かせます。この環境では、sandbox.excludedCommands に何も足さずに uloop が動きました。信頼できるプロジェクトだけに入れます。次に Editor を占有する時間は、こうだいさんと決めます。

離す側については、注入の最後にボタンの状態を 0 へ戻さないと押しっぱなしになる、という報告があります [5]。試験では、離したあとに札が手札へ戻り、押しっぱなしにはなりませんでした。
