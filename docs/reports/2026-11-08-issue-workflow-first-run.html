04Bash の場所

作業は cd で作業フォルダに移って行われました

Bash は、エージェントがシェルのコマンドを打つ道具です。作業フォルダ（cwd）は、コマンドを打つときにいるフォルダのことです。今回は、ブランチごとに別のフォルダを開く git の仕組み（worktree）で作った作業フォルダを使いました。

  • 9体動いたエージェント
  • 178回Bash の呼び出し
  • 147回作業フォルダへ移った

確かめた事実

  • 動いたエージェントは 9 体です。内訳は、実装役 3 体と確認役 6 体で、確認役は 1 回目 3 体とやり直し 3 体でした。直し役は 0 体でした。
  • 作業記録（サブエージェントが残した記録）の作業フォルダの欄は、9 体すべてで C:\Users\user\orca\original-card-battle でした。これは main の checkout、つまり手元のリポジトリの本体です。
  • Bash の呼び出しは 178 回でした。そのうち 147 回は、コマンドの中で worktree のパスへ cd するか、そのパスを直接指していました。残りの 31 回は、空きメモリの計測、gh issue view（Issue の内容を見るコマンド）、一時フォルダのログの読み取りでした。
  • 実装役 #826 は 1 回だけ、main の checkout で gh issue view と git fetch（リモートの取得）を打っていました。どちらも読むことと取得だけでした。
  • 3 つの commit は、どれも「cd 作業フォルダ && git commit」の形で打たれていました。
  • 試験のあと、main の checkout の git status と HEAD（d422bbe7）は、始めたときと変わりませんでした。

推定

Bash は呼ぶたびに main の checkout から始まるとみられます。そのため、cd を付け忘れたコマンドは main の checkout で動きます。今回は付け忘れがありませんでした。守っているのは、起動の指示文（プロンプト）の指示だけです。

05hook の反応

3 つの hook は、エージェントのコマンドに一度も反応しませんでした

hook は、コマンドの実行の前に動いて、通す・止める・確認するを決める仕組みです。見たのは 3 つです。pre-issue-create-guard は Issue の作成を、pre-commit-tracker-guard は進捗の記録（tracker）と実装を同じ commit に入れることを止めます。merge-gate は PR の merge を、確認するか拒むかを決めます[7]。

  • 3つ見た hook の数
  • 0回エージェントの反応
  • 3回止められなかった commit

確かめた事実

  • 9 体の作業記録のどこにも、3 つの hook が止める・確認する・拒むと出した跡はありませんでした。
  • エージェントは gh issue create も gh pr merge も打っていません。git commit は 3 回打たれ、どれも止められていません。
  • 作業記録に残る hook は、画面に出力を返した hook だけでした。何も出さずに通した hook は記録に残らないため、プロジェクトの hook が動いたかどうかは記録からは確かめられません。
  • 模擬の入力を hook に渡して判定を見ました。merge-gate は、作業フォルダが main の checkout なら「確認する（ask）」を返しました。wf-826（#826 のために作った作業フォルダ）なら「拒む（deny）」を返しました。pre-issue-create-guard は、main の checkout の hook のファイルで判定すると通しました（終了コード 0）。wf-826 の中の hook のファイルなら止めました（終了コード 2。2 は止める合図です）。
  • pre-commit-tracker-guard は、hook のファイルがある場所を基準に index（commit に入る変更の一覧）を見る作りでした。その場所は main の checkout でした（.claude/hooks/pre-commit-tracker-guard.sh の REPO_ROOT）。

推定

このセッションの hook は、main の checkout のファイルで動いたとみられます。エージェントの作業フォルダも、main の checkout として渡ったとみられます。そのため、エージェントが Issue を作っても pre-issue-create-guard は通すとみられます。tracker を混ぜた commit も見逃し、merge は拒む（deny）のではなく確認する（ask）になるとみられます。

この結果は、前提の「hook はエージェントを守りきれない」と合います。

07手順の穴

スキルの手順どおりには動かない所がありました

  • 4つ見つけた手順の穴
  • 72件OWNER だった Issue
  • 1回例外を足した回数

確かめた事実

  • gh issue list（Issue の一覧を出す GitHub のコマンド）には、authorAssociation（書いた人と repo の関係の欄）がありません。そのため、スキルの手順 3 のコマンドは失敗しました。gh api で Issue の一覧を取り直すと、72 件すべてが OWNER（持ち主）でした。
  • Workflow（複数のエージェントを順に動かす仕組み）で、~/.claude のスキルの台本を scriptPath（台本のファイルの場所を渡す引数）に渡しました。すると、Read のあとでも「読めるファイルではない」と拒まれました。台本の全文をそのまま渡して起動しました。
  • 確認役が PR を開いても、URL の欄を空で返すことがあり、台本の判定が pr_missing になりました（#826）。
  • 確認の合格の条件は「すべて exit 0（すべて成功の終了コード）」です。そのため main が赤いと、すべての PR が止まります。今回は、メインのチャットの判断で 1 回だけ例外を足しました。

ほかに気づいたことは、次のとおりです。

  • #947 の実装役は、完了条件の grep を満たすため、作業の範囲（Scope）にない BackdropSpec.cs のコメント 1 行の旧い名前も消しました。この変更は PR #949 に入っています。
  • PR #948 は、PR #943 と同じ battle_core_v4.md などのファイルを触ります。記録には、#898 と CardCatalog などのファイルも同時に触るとあります。後から merge するほうは、もう一方に積み直す必要があります。
  • 試験の記録を進捗の記録（tracker）に入れる作業は、まだしていません。issue-workflow の設定の「実行のあと」の 8 番にあたる作業です。
  • 申し送り（担当へ渡すメモ）は、試験の前に 4 件を回収し、Issue #945・#946・#947 にまとめました。試験のあとに 1 件を回収して Issue #951 にしました[5]。回収したファイルは消しました。PR を開いた wf-826・wf-947・wf-837 の作業フォルダは外しました。ブランチは手元と origin（GitHub 上のリモート）に残っています。

推定

同じ穴は、次の試験でも起きるとみられます。確認の合格条件（すべて exit 0）は、main が赤いままなら、次の試験でも全部の PR を止めるためです。

09次に判断が要る点

merge の順番と、規則の読み方を決めてください

  1. merge の順番です。推奨は、PR #943 を先に merge し、その後に #948 を積み直すことです。main の赤が消え、#948 の確認も例外なしで通るためです。
  2. #826 の規則の読み方の確認です。実装役が battle_core_v4.md の §4 と §15 に書いた読み方は 4 つです。このまま進めてよいかを決めてください。
    • 受けるダメージの 2 倍は、攻撃の撃だけに掛けます（壁・出血・見切りの返しには掛けません）。
    • 覚醒の Guard（防御の値）+5 は、防御の札か、面に Guard の値を持つ札だけに付きます。
    • 覚醒の移動 +1 は、自分の移動だけに足します（押す・引くには足しません）。
    • 2 つのスタンスは、敵が持っても同じように効きます。
  3. Unity Editor での確認です。merge のあとに、Unity Editor で #948 と #950 の手触りを確かめます。確認が済んだら、Refs にした #826 と #837 を閉じます。
  4. スキルの穴を直すかどうかです。gh の欄・scriptPath・URL の欄の 3 点を、dotfiles（個人の Claude 設定のリポジトリ）側で直すかを決めてください。
