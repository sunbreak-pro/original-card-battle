# JS extensions designed from the documents

Rules the design documents define but the C# in `unity-port/` does not have yet. Each one is **opt-in**: with no option set, every ported module behaves exactly as the C# (the parity harness and every ported unit test stay as they are). The game turns an extension on through one flag per module, named in its section. When the C# lands, it wins and the extension is replaced by its port.

Sources are under `.claude/docs/` unless a path says otherwise. Each job owns its own section below and edits only that section. Where a document is silent, the choice is listed under 「試作で決めたこと」 with its reason.

## 出立の枠（DeckLimits）— the survivor's bonus at 出立

Job: limits. Files: `src/core/battle/DeckRules.js` (`DeckLimits`; `DeckRules.ValidateDeck` / `CanAdd` / `Validate`), `src/core/battle/Cards.js` (`Cards.Validate`), `src/bridge/depiction/DeckBuilder.js`, `src/bridge/depiction/DepartureBuilder.js`, the 出立 screen (`src/scenes/meta/departure.js`, `DepartureSupplies.js`, the `.ocbg-meta-bonus` and `.ocbg-meta-decklist` rules in `meta.css`). Tests: `test/ext/limits.test.mjs` (L-1〜L-9, and the hand-off tests that follow 出立する through the shared contract).

**Flag: a `DeckLimits` passed as the trailing optional argument.** Left out (or `null`) it is `DeckLimits.Default`, the C# constants (deck 20〜40, 3 tool slots, 3 consumable slots), and every check, line and title is the C#'s byte for byte.

```js
import { DeckLimits } from 'src/core/battle/DeckRules.js';
new DeckLimits({ DeckMin, DeckMax, ToolSlots, ConsumableSlots })   // a key left out (or null) is the default's; frozen
DeckLimits.Default                                                  // { 20, 40, 3, 3 } = Constants.DeckMin / DeckMax, DeckRules.ToolSlots / ConsumableSlots
DeckLimits.From(x)                                                  // null → Default, a DeckLimits as is, else read by the four keys (Inheritance.startLife's LifeStart)
limits.IsDefault · limits.With({...}) · limits.Equals(other)

Cards.Validate(deck, limits = null /* = Default */)
DeckRules.ValidateDeck(deck, owned, limits = DeckLimits.Default)
DeckRules.CanAdd(deck, id, owned, limits = DeckLimits.Default)
DeckRules.Validate(departure, owned, limits = DeckLimits.Default)
new DeckBuilder(owned = null, limits = DeckLimits.Default)          // .Limits; CanAdd / Add / Validate / IsValid / StatusText read it
  builder.Title · DeckBuilder.TitleFor(limits) · builder.RaisedLine  // static DeckBuilder.Title stays the C#'s
  DeckBuilder.Random(seed, size = 30, limits) · Prototype(limits) · Load(saved, limits) · Read(saved, limits)
  DeckBuilder.LoadOrPrototype(saved, text[, out][, limits])          // a DeckLimits as the last argument is the limits, not the out flag
  DeckBuilder.ReadOverCap(saved, limits) → { ok, value }             // Read, but a string past the cap keeps every card (試作 7)
  DeckBuilder.OverCapNotice(total, limits) · builder.WithOwned(owned) // the reason line; the deck on the owned kinds, over the cap kept
  DeckBuilder.WithPrototypeKinds(kinds)                              // kinds ∪ the prototype deck's kinds (L-8)
new DepartureBuilder(tools, consumables, limits = DeckLimits.Default) // .Limits; CanAddTool / CanAddConsumable / ToolsLine / ConsumablesLine read it
  builder.Title / ToolHeading / ConsumableHeading · DepartureBuilder.TitleFor / ToolHeadingFor / ConsumableHeadingFor(limits)
  builder.RaisedLine · builder.IsBonusToolSlot(i) · DepartureBuilder.BonusLabel
  builder.Validate(deck) / CanSetOut(deck)                           // the deck's bounds from deck.Limits, the slots from builder.Limits
DepartureSupplies.NewBuilder(limits)
DepartureSupplies.Carry(departure, limits)                         // { battleToolIds, consumableIds, loadout } — what 出立する hands on
mountDeparture(host, ctx)                                           // limits = DeckLimits.From(ctx.lifeStart); onSetOut payload gains `limits`
```

### 試作で決めたこと

1. **The bonus raises only the tool slots and the deck cap.** The consumables stay 3, the floor stays 20 and a kind stays at 3 copies. concept-v3 §14 names only 「ツール枠 +1、デッキ上限 +5」.
2. **A deck builder's limits hold the deck; a departure builder's hold the slots.** `DepartureBuilder.Validate(deck)` checks the deck against `deck.Limits` (what `deck.IsValid` reads) and the slots against its own, so `StatusText` and `CanSetOut` never disagree. The documents do not split the screen this finely; the screen makes both from the same limits anyway.
3. **`Cards.Validate(deck, limits = null)`** reads `limits.DeckMin` / `DeckMax` and treats null as Default instead of writing `= DeckLimits.Default`: `DeckRules.js` imports `Cards.js`, and importing back would add a module cycle through `TurnLoop.js`. The behaviour is the same.
4. **The static texts stay the C#'s; instance getters of the same names print the limits.** `DeckBuilder.Title` (static) is the C#'s 20〜40; `builder.Title` is the builder's. Same for `DepartureBuilder.Title` / `ToolHeading` / `ConsumableHeading`. The static `…For(limits)` forms are for a screen without a builder.
5. **The prototype deck's kinds join the departure's owned kinds** (`DeckBuilder.WithPrototypeKinds`), on the router's list or on `Expedition.InitialKinds` when the router passes none. The documents give a new heir the initial forty and say nothing of the prototype deck; the C# `Expedition` owns its start deck's kinds anyway, so this is what the C# would own once the life begins.
6. **出立 repeats the bonus beside the step it raises.** The documents put the showing of the bonus in 継承の間, not in 出立: camp §3.1 継承の間 → 前回生存者 「生存者ボーナスの内容を表示」 and tier1-core R1-14 「継承の間（遺産選択 / 生存者ボーナス確認 / …）」; the hall already does it (`Inheritance.survivorView` → `src/scenes/meta/hall.js`). camp §3.2 出立 lists only ツール選択 / 戦闘デッキ構築 / 出発 and says nothing about it. The screen still shows 「生存者ボーナス　デッキ上限 +5（40 → 45）」 beside the deck step's title, 「生存者ボーナス　ツール枠 +1（3 → 4）」 beside the supplies step's, and draws the 4th tool slot with the wick border (tooltip 「生存者ボーナス」). Reason: 出立 is where the raised numbers are used, and without a word there the title's 20〜45 and the 4th slot look like the normal rules, the opposite of concept-v3 §14's 「次の 1 生だけ」; one line beside the title costs nothing and changes no rule. The words reuse the hall's (`InheritanceText.SurvivorTools` / `SurvivorDeck`) under the label 「生存者ボーナス」 (concept-v3 §14), so the hall and 出立 say the same thing. They come from the bridge (`builder.RaisedLine`, `DepartureBuilder.BonusLabel`) and are "" on a life without the bonus, so a first life's 出立 shows nothing new. camp §3.1 still says the bonus is 「§12-12 で未確定」; concept-v3 §14 (2026-09-16) decided it and wins.
7. **A saved deck string past the cap opens whole, over the cap, and says why** (`DeckBuilder.ReadOverCap`, used by 出立 for the router's saved deck and for its own draft). A 45-card string saved in a bonus life, opened in the next life without the bonus, keeps all 45 cards on a builder held to 40: ＋ stays greyed out, `Validate` fails, `StatusText` reads 「45 枚です。あと 5 枚外すと戦えます」 and the notice reads 「生存者ボーナスが終わり、デッキ上限が 40 枚に戻りました。保存したデッキ 45 枚から、外す 5 枚を選んでください」 (`OverCapNotice`; a cap above the C#'s 40 gets 「この生のデッキ上限は 45 枚です。…」 instead). The notice goes once the deck is back under the cap. Reason: concept-v3 §14 makes the +5 last 「次の 1 生だけ」, so the next heir must fit the deck to 40 again; an empty deck (what the C# `Read` gives for any string `Add` refuses, and what this decision said until 2026-10-21) threw the whole build away under a notice meant for broken saves, and cutting the deck to 40 would pick the five cards for the player. Any other fault (a 4th copy, an unknown card, stray text) still reads as the C#'s empty deck and notice; `Read`, `Load` and `LoadOrPrototype` stay the C#'s. The C# never meets the case: without the bonus no deck string passes 40.
8. **`LoadOrPrototype` takes the limits as its last argument** and tells them from the C#'s `out` flag by type (`instanceof DeckLimits`), so the existing two- and three-argument calls keep their meaning.

### For the router and the other jobs

- `mountDeparture`'s `onSetOut` payload carries `limits` (a `DeckLimits`) and `loadout`, the DungeonContent `Loadout` with the life's slot count (`DepartureSupplies.Carry(departure, limits)` makes `battleToolIds`, `consumableIds` and `loadout`; tested without a DOM).
- The router may pass `owned` = `Expedition.InitialKinds` ∪ the prototype deck's kinds; the screen unions them itself either way.
- **Open — the wiring the game needs before a survivor can use the bonus (not this job's files).** Until it lands, 出立する with any tool, or a survivor's deck of 41〜45, ends on a black screen. Both changes were applied to a scratch copy and checked: the full unit suite passes, survivor lives set out with 45 cards and 4 tools, fight, grow to 45 and replay to the same state, and the real app reaches the first battle with no console errors (the hand-off tests 「L-2 / L-3 / L-5 hand-off」 in `test/ext/limits.test.mjs` follow the same path).
  - `src/app/life.js` (integrator): `choiceToData(choice, toolSlots)` saves the departure's `Loadout` as `runLoadoutToData(toRunLoadout(choice.loadout, toolSlots))` (a `RunLoadout` as it is; `makeStart` passes `lifeStart.ToolSlots`), `loadoutFromData` is `runLoadoutFromData` (a save without `trial` reads as the C#'s), and `lifeSetup` passes `{ limits }` with `limits = DeckLimits.From({ DeckMax: start.deckMax, ToolSlots: start.toolSlots })` (`null` options when `limits.IsDefault`). Today `choiceToData` reads the `Loadout`'s `ItemDef`s as relief items with `Kind` null and `new RunLoadout(…)` throws 「a tool thins the air for the whole life, so it lowers density」, and `new Expedition(…)` without the limits throws 「Deck has 45 cards; the maximum is 40.」. `main.js` needs no change (`makeStart` already saves `toolSlots` / `deckMax`). The WORLD job's `trial: true` goes into the same options object when the game turns it on.
  - `src/bridge/depiction/BattleLaunch.js` (multi-enemy team): a `this.Limits = null` field and `Cards.Validate(this.Deck, this.Limits ?? null)` in `BuildDeck()`. `EncounterBattle.NextLaunch` already sets `launch.Limits`; today `BuildDeck()` ignores it and a 41〜45-card deck throws at the first fight (「BattleLaunch: the deck breaks §8 — Deck has 45 cards; the maximum is 40.」). The `todo` test 「L-3 hand-off」 turns into a pass once it lands. `DemoSession.js` (the demo only) has the same call.

## 手記の敵の頁と地図の敵の情報（JournalIntel / EnemyPages）— the journal's enemy pages and the map's enemy intel

Job: journal. Files: `src/bridge/journal/EnemyPages.js` (new: the pages' data and texts), `src/app/intel.js` (`JournalIntel`, the `IEnemyIntel` the game plugs in, and the two raises it writes into the journal), `src/scenes/meta/journal.js` (the drawer: one tab per enemy fought in battle, the fight's pages at the battle's 開示度, every enemy page ending on 自分のメモ; `bookOf` / `tabsOf` exported for the tests), `src/scenes/meta/meta.css` (the drawer's tab rules only), `src/scenes/meta/text.js` (`EnemyTab` removed). Tests: `test/ext/journal.test.mjs` (J-1〜J-16). Dev page: `dev/journal-ext.js` (`node tools/devbuild.mjs dev/journal-ext.js`; `#explore`, `#explore-map`, `#battle`, `?surveyed=1`, `?layer=N`, `?node=elite|boss`, `?trial=1`, `?journal={…}`).

**Flag: the intel handed to the Expedition (and so to its ExplorationSession), then bound.** Left out, the session uses the C#'s `NoEnemyIntel`: every combat node says 「敵: ？」, the journal has the one 「敵の頁はまだありません」 page, and no node raises the journal — byte for byte the C# (J-12). The game passes a `JournalIntel` and binds it (`src/app/life.js` `lifeSetup`). No ported module changed. `bind` wraps the session instance's own `Arrived` (the one place a node resolves), so the intel's two raises run inside the call the recorder logs.

**One value for every screen.** The map, the journal and the battle's omens all read `Expedition.DisclosureOf` (concept-v3 §5: the omens' precision is the journal's 開示度). The survey and 七層 write into that journal; nothing is raised only on a screen.

### 試作で決めたこと

1. **The page's rows follow `battle_ui_ux_v2.md` §7: the 傾向 at 1, not 2.** §7's 「手記の敵の頁」 column gives the bands at 開示度 1 and 弱点 / 特殊行動 / 適応条件 at 2; roster §1.1 only says all of it reads at 2. The map's 傾向 line is a different place: `dungeon_exploration_v4.md` §6.3 adds it at 2, and the map does (J-7). The C#'s test stand-in (`ExplorationSessionTests.RecordingIntel`, a row 「傾向」 at 2) is a fixture, not the page.
2. **名前 and HP 最大 at 0.** §7 gives a page at 0 「名前と HP 最大だけ」. Such a page exists only in battle, for a foe met for the first time; the map names nobody below 1 (§6.3) and the journal lists no one below 1.
3. **得意な間合い is a row (at 1) and is the map's 傾向 line.** The roster gives it in every section heading as the summary of the decision tree (§1.2 「得意な間合いと居続け対策」). The map's node panel has room for one short line, and the C#'s own example line has that shape (「傾向: 間合い 1〜2 で突く」).
4. **特殊行動 = 構え + 崩し + a boss's 専用の状態.** No document defines the row's content for the v4 enemies. The stance is the one action a fight uses once and keeps (roster §1.2); §7's 「崩しの有無」 has no row of its own in §2.4's row list, so the 崩し actions sit here; a boss's own statuses are what only it does. Each line is the roster's cells: 「鉄壁（構え）: 毎ターン開始に Guard +3」, 「打ち下ろし（攻撃）: 威力 8、崩しを 1 付与する。間合い 0: 崩し +1」, 「瘴気纏い（相手に付ける）: …（戦闘終了まで）」 — 「相手に付ける」 is the terms page's word (`JournalTerms`) for the roster's 向き 「相手に」, so the drawer's two pages say it the same way. セルク's 崩し comes only from its adaptation breaker, so it is read in 適応条件, not here.
5. **適応条件 lists every row of the boss's table, the stages included** (their condition is 「手記の文」 as well), one a line, without the 「」.
6. **The survey's target: boss → elites → plain fights, the first below 2.** §5 の 4 leaves the choice to the layer. The layer's master is the fight no route avoids, so the survey shows it first; an enemy already at 2 would make the survey do nothing, so the rule moves on to the next one. It is asked when the node resolves and written into the journal then, so a later raise (観察, a trace page) cannot move it to another enemy, and a reload asks at the same logged moment.
7. **Pages in roster order**, not in the order met: the Expedition keeps the 開示度 as a dictionary with no order a replay or an inherited journal would keep.
8. **One memo per life.** The router keeps one memo text (`live.memo`), so every enemy page shows that one memo (no memo per enemy). Empty, it reads 「メモはまだありません。」 (the C#'s memo page). While exploring the row has no 「戦闘中は書けない」.
9. **竜神 (`dragon_god`) has no page**: it is not in the core yet. When it lands, its texts are roster §7.13 (手記の頁) and §7.11 (適応).
10. **歪みの根 at 2 from the arrival on 七層, not from the life's start.** `seven_layers_v4.md` §4 / §9 の 2 propose 「最初から開示度 2」 and leave it 未確定; the prototype applies it. 「最初から」 is read as "before the root is ever met, without a survey", given the moment the life sets foot on 七層: the root is fought only there, so every screen that shows it (七層's map, its battle) reads 2 either way, and a life that never reached 七層 does not carry — and leave in its trace as a legacy pick (Inheritance `buildCandidates` lists every enemy of the dead life's journal) — a page every heir would get anyway. It is written into the Expedition's journal, so the omens read it (J-15). Nothing happens on the 七層 node that ended the life by 瘴気.
11. **Exploring, the 敵 tab is one tab with a row of per-enemy tabs below it.** §2.4's 「戦っている敵ごとに 1 つ」 is the battle's (at most three foes). Exploring, the journal holds every enemy met (up to 13), more than one row of a 30% drawer holds, so the enemies sit on a second row under the tab labelled 「敵」 (`JournalBook.TabLabel`, §6.7 「タブは「敵・ダンジョン・メモ」の 3 つに…」). With five or six tabs in battle the labels are set smaller so a five-letter name keeps one line.
12. **The intel writes the raises through the session's `Arrived`.** The trial rules (the world job's) already ask the intel at that moment; with them off the C# session asks nothing, so `bind` wraps the session instance's `Arrived` and the intel makes the same write there. Arrival is where the session draws a node's encounter, so it is the one moment a replay is sure to repeat.

### 試作で決めたこと

1. **A consumable that would change nothing now cannot be used** (薬草 at full HP, 濃い干し肉 at +4, 忘れ水 at full stamina, 浄化の香 at 0%); the slot says 「いま使っても何も変わらない」. The documents are silent; the game should not offer a choice that does nothing. **「Changes something now」 has one definition: the slot's forecast is not empty** — the gauge, max stamina, stamina or HP the screen shows would move (`ChangeLines` in `ExplorationScreenBuilder.js`, read by both `ExplorationSession.CanUseSlot` and the slot card). So 濃い干し肉 at temporary −4 with 瘴気 ≥ 80% (10 − 4 − 4 = 2, held on the floor of 3; +1 still shows 3) is not offered: the hidden temporary change the floor swallows counts as nothing, the simplest reading of 「now」.
2. **Copies of a tool add** (刻限の砂 ×2 = +2, 灯芯の欠片 ×2 = +30%). tools §6 の 1 lets a tool fill two slots, and the C#'s `Loadout.TimeLimitBonus` already sums the copies.
3. **標の石 may land on any unresolved node, the boss included.** §3 names no exception, and encounters §4.3 (七層) counts 歪みの根 among the places a jump reaches.
4. **標の石 is aimed first**: the first press marks the stone and the map marks where it can land, with each landing's forecast and 「跳ぶ」; Esc, 「やめる」 or the slot again stops without spending it. Using another slot that can be used stops the aim and uses that slot; pressing one that cannot be used (or its key 1〜3) is refused and changes nothing, so the stone stays aimed. Opening 「この生を終える」 stops the aim (the card covers the map, as Cancel already did), so a life never ends with a stone still aimed. The documents do not say how the target is picked.
5. **特殊な食事 never kills: HP stops at 1.** §5 says HP falls by 10% and nothing of an event ending a life.
6. **The chest's card is a deal from the card pile, 3 to pick 1** (the battle's card reward). §5 says 「カード 1 枚」; §4.3 counts the chest's card among the pile's draws and lays the pile out three at a time.
7. **A chest's draws use `Expedition.RewardSeed` of its node** (an event node never holds a battle, so the seed is free).
8. **Layers 4〜6 hold no event node** (seven_layers_v4.md §4). Should a map give them one, they draw from §5's own extension of the line (泉 20 / 10 / 0, 重い宝箱 50 / 60 / 70, 特殊な食事 30), a 泉 heals 30% and a chest holds layer 3's.
9. **The 泉 asks nothing and resolves on arrival.** §5 gives 「受ける / 受けない」 to the chest and the meal only.
10. **写しの帳's choices are the layer's encounter table, those still below 開示度 2**; with none left the survey asks nothing. 「この階層の敵 1 種」 read as the enemies this layer's nodes can field.
11. **A lower maximum pulls current stamina down with it (the chest); a higher one does not refill.** The same as the core's step (`min(max, …)`).
12. **Finds take the free slots first, in the order found; the rest wait one swap card each.** While a swap waits, the slots cannot be used (「その場で入れ替えるか諦めます」).
13. **A declined event shows no result card** (nothing changed); the journal still records 「受けなかった」.
14. **An event on the node that spends the last 刻限 still happens** and is answered before the layer-break card (the node was entered and paid for, as a fight on that node still happens in the C#).
15. **The trial buttons and cards are their own enums** (`TrialAction`, `TrialCardKind`): `ScreenAction` and `CardKind` keep the C#'s members and order. `ReliefKind` takes new members after the C#'s two.

### For the integrator

- `src/app/life.js` may pass the lineage's knowledge explicitly: `new Expedition(…, { trial: true, limits, carvingKnown: start.carvingKnown })` (or `new RunStart({ …, CarvingKnown: start.carvingKnown })`). Without it the session reads the map seam, which gives the same answer.
- `src/app/recorder.js` needs nothing: `PendingResult`, `PendingTaken`, `OfferFits` and `DeckMax` are getters (not logged); `CloseResult`, `CloseTaken`, `OpenTraining` and `PutOffTraining` are logged calls (no arguments) and `ShowTaken(card)` one with plain data, which the replay repeats; `TurnDownFind` is called by the session and the expedition on themselves, never through the proxy.
- `src/app/main.js` `inheritance.take` refuses a take once the life is over (`raw.Session.State.IsOver`), as the scene does, and returns `Taken` with `Result` (what `Inherit` did, plus which 走り書き were new); `inheritance.scribbles()` gives the 走り書き the life carries, for the trace card.
